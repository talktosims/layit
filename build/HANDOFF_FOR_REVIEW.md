## 1. What is being built

A laser tile-pattern projector. ESP32-S3 receives tile vertex data over WiFi/WebSocket from a phone PWA (already shipped, separate codebase), drives a dual-channel SPI DAC (MCP4822) → op-amp buffer (TL072) → analog inputs of a 20K PPS galvanometer scanner driver, with TTL-blanked 200mW 520nm laser drawing the outlines, and an OV5640 camera providing optional vision-based alignment correction. Class 3B laser; safety interlock on enclosure lid.

## 3. Bugs found in Rev 1.0 and the fixes applied

Numbering matches `FIXES_v1.md`. Each fix lists my confidence level and the engineering reasoning.

### F-1 — U1 (AMS1117-5.0) overheats 🔴 CRITICAL

**Bug:** Original design cascades AMS1117-5.0 → AMS1117-3.3. U1 carries the entire 3.3V load (700mA peak ESP32+camera+LED) at 7V drop = ~5W. SOT-223 thermal limit ~1W with PCB pour. U1 fails.

**Source:** [`LayIt_Laser_Circuit_Description.md`](LayIt_Hardware/schematic/LayIt_Laser_Circuit_Description.md) lines 116-118 — doc itself acknowledges thermal calculation but only fixes U2's heat, not U1's.

**Fix applied:** Replace U1 with MP1584EN buck converter module (4-pin breakout: VIN, GND, VOUT, EN). Set output to 5.0V via onboard trim pot before installing. PCB now has 4-pin 0.1" header in U1 location.

**Confidence:** 🟢 High. Standard thermal math; MP1584 is a textbook step-down for this voltage drop and current.

**Codex please verify:**
- Is buck regulator switching noise (typically ~500kHz on MP1584) acceptable for the 5V rail powering MCP4822 + TL072? Both are analog-adjacent. Suggest LC filter on output if so.
- Is there a smaller / cleaner alternative I should have picked (e.g. TPS54302 in SOT-23-6 footprint that fits the existing PCB without a module)?

### F-2 — Laser fires at boot 🔴 CRITICAL SAFETY

**Bug:** Q1 (2N7000) gate has no pull-up. ESP32 GPIO14 default at boot is high-impedance INPUT until firmware runs `pinMode(OUTPUT)`. During the ~50-200ms boot window, gate floats LOW → MOSFET OFF → R9 (4.7K) pulls TTL to 12V → laser fires.

**Source:** [`LayIt_Laser.ino:298-299`](LayIt_Hardware/firmware/LayIt_Laser.ino) confirms firmware sets HIGH for safety, but only after boot.

**Fix applied:** Add R16 (10K, 0805) from Q1 gate to +3.3V. With pull-up, gate is HIGH at boot → MOSFET ON → drain pulled LOW → TTL LOW → laser OFF until firmware confirms.

**Confidence:** 🟢 High.

**Codex please verify:**
- 10K is the standard value but is it appropriate given R10 (100Ω series) ahead of it on the gate path? Should the pull-up be on the ESP32 side of R10, or on the gate side?

### F-3 — Camera D8/D9 on ESP32-S3 strapping pins 🔴 CRITICAL

**Bug:** [`LayIt_Laser.ino:66-67`](LayIt_Hardware/firmware/LayIt_Laser.ino) had `PIN_CAM_D8 = 45` and `PIN_CAM_D9 = 46`. GPIO45 is VDD_SPI strap; GPIO46 is download-mode strap (HIGH at boot triggers ROM bootloader). If camera asserts D9 at startup, ESP32 fails to boot firmware.

**Fix applied:** Moved to `PIN_CAM_D8 = 40`, `PIN_CAM_D9 = 41`. Both are general-purpose, exposed on WROOM-1 N16R8, no strapping role.

**Confidence:** 🟢 High. Espressif's official ESP-EYE / S3-CAM reference designs avoid 45/46 for this reason.

**Codex please verify:**
- For ESP32-S3-WROOM-1 N16R8 specifically (which uses internal Octal PSRAM occupying GPIO33-37), are 40/41 truly unrestricted? Datasheet table 2-2 should confirm.
- The camera (OV5640) module's reset/PWDN handling — is the pull-up on RESET (R13) and pull-down on PWDN (R14) keeping the camera quiet enough at ESP32 boot, or does the camera drive D8/D9 immediately?

### F-4 — SMD parts vs perfboard 🔴 CRITICAL

**Bug:** BOM v3 specifies 0805 SMD passives, ESP32-S3-WROOM-1 castellated SMD module, FPC SMT connector, USB-C SMT receptacle. Binder describes through-hole perfboard build ("bend legs 90°, push through holes, clip flush"). Fundamentally incompatible — SMD parts have no leads to push through.

**Fix applied:** Two-part solution:
- For the bare WROOM-1 module: bought ESP32-S3-DevKitC-1 dev boards (N16R8 chip on a 0.1" pinned breakout PCB). Drops into perfboard. Built-in USB-C, BOOT, RESET — eliminates J2/SW1/SW2/U1 from the BOM.
- For 0805 R/C, SOT-223 reg, SMA diode, WS2812B: hand-solder them straddling adjacent perfboard pads. Tedious but feasible.
- For the FPC 24-pin (J5): the user's OV5640 module likely has its FPC connector pre-attached on its own PCB, so J5 is moot.

**Confidence:** 🟡 Medium. The dev-board path is well-trodden; the SMD-on-perfboard hand-solder path works but is fiddly for a beginner.

**Codex please verify:**
- Is there a simpler path I'm missing? Some users get cheap "ESP32-S3 to DIP" adapter PCBs (~$3 on AliExpress). Is one of these a better fit than the dev board, given Robbie already owns the bare WROOM-1?
- For the user's specific OV5640 listing (he'd need to share the link), does the FPC come pre-attached?

### F-5 — Op-amp topology incorrect 🟡 MAJOR

**Bug:** [`LayIt_Laser_Circuit_Description.md` lines 204-216](LayIt_Hardware/schematic/LayIt_Laser_Circuit_Description.md) shows R5 going to TL072 (+) input and R6 in feedback. Doc quotes both "non-inverting gain 3.4×" AND "inverting gain 2.4×" as possibilities. As drawn, the circuit has no defined feedback ratio and the op-amp would saturate.

**Fix applied:** Reconfigure both TL072 channels as **unity-gain voltage followers**: DAC output → (+) input directly, (-) input → output directly, no R5/R6/R7/R8. Removed those four resistors from BOM.

**Confidence:** 🟡 Medium. **This is the biggest open question for the build.** The original design implied a gain stage was needed to scale 0-4.096V DAC output to whatever the galvo driver wants. Without knowing the specific galvo driver's input requirements, unity-gain may give insufficient deflection range.

**Codex please verify:**
- For typical "20K PPS dual-axis galvo scanner kit + driver" boards from AliExpress/eBay (around $70-120), what's the standard input voltage range? Most I've seen accept ±5V differential or 0-5V single-ended. The user has not yet identified his specific driver model.
- If galvos require ±5V differential, the single-supply TL072 (V+=12V, V-=GND) cannot output negative voltages. Suggested fix: ICL7660 charge pump for -12V rail. Is that the right call, or is there a simpler topology (e.g. virtual ground at +6V on the driver's signal-ground input)?

### F-6 — Single-supply op-amp can't drive bipolar galvos 🟡 MAJOR

**Linked to F-5.** Mentioned but not resolved without galvo spec.

### F-7 — Safety interlock wiring inverted 🟡 MAJOR SAFETY

**Bug:** Binder Section 4 says "Connect the switch's COM and NC (Normally Closed) terminals to the SW3 pads." Section circuit description says "Lid ON = switch is pressed (contacts CLOSED) = GPIO47 reads LOW = safe." A microswitch's NC terminal is *open* when pressed, not closed. So as binder-instructed, lid-closed reads UNSAFE and lid-open reads SAFE — backwards.

**Fix applied:** Documentation now specifies COM + **NO** terminals (verified: NO closes when lever is pressed by lid). Multimeter test in build addendum: lid-closed should beep, lid-open should not.

**Confidence:** 🟢 High. Microswitch behavior is unambiguous.

### F-8 — Missing R3, R4 (USB-C CC) 🟡 MAJOR

**Bug:** Schematic includes R3, R4 (5.1K each, USB-C CC1/CC2 → GND, required for USB-C device-mode enumeration). Binder Section 2 parts checklist omits them.

**Fix applied:** Added to BOM v4. Note: with the ESP32-S3-DevKitC-1 swap, the on-PCB USB-C (J2) becomes optional anyway — dev board has its own. R3, R4 only needed if user keeps J2 for redundant programming path.

**Confidence:** 🟢 High.

### F-9 — Missing MPU6050 IMU 🟡 MAJOR

**Bug:** BOM v3 line 25 lists MPU6050 GY-521. Firmware uses it (`setupIMU`, `readIMU` in `LayIt_Laser.ino` lines 327, 380-385). Binder build instructions don't include installing it.

**Fix applied:** Added to BOM v4 as explicit step. Wiring: VCC→3.3V, GND→GND, SDA→GPIO1 (shared bus), SCL→GPIO2 (shared bus). I2C address 0x68 doesn't conflict with OV5640 (0x3C).

**Confidence:** 🟢 High for I2C bus-sharing; 🟡 Medium that user's specific OV5640 module's I2C address is actually 0x3C and not 0x60 (some variants).

### F-10..F-13 — moderate items

- ESD protection (TVS diodes) added to BOM, optional — user can skip
- Schottky drop documented (~0.4V, leaves 11.6V rail) — operationally fine
- WS2812B series resistor R17 = 470Ω added — defensive
- Original schematic file format (KiCad 7) supersedes — PCB rebuilt from scratch via Python script using KiCad 10 footprints

## 5. What was NOT changed and may still need attention

- **Schematic file** (.kicad_sch) — never regenerated. PCB was rebuilt from scratch as a Python-generated layout, but the schematic remains in its broken Rev 1.0 form. Either regenerate the schematic via KiCad's "Update Schematic from PCB" or hand-redraw.
- **Copper traces** — `LayIt_Laser.kicad_pcb` has all footprints placed but **no traces routed**. Connection netlist relies on the schematic which doesn't load in KiCad 10. Before fab, traces must be added (auto-router or manual) using the pin-assignment table in `LayIt_Laser_Circuit_Description.md` Section 3 as the netlist source of truth.
- **Galvo driver compatibility** — see F-5/F-6. Open question.
- **Antenna keepout** — KiCad design has no keepout zone defined for the ESP32-S3 antenna section. Needs to be added before fab routing.
- **Class 3B regulatory compliance** (FDA/CDRH 21 CFR 1040.10) — required before any commercial sale. Not in scope of this review.
- **Vision-correction system** (firmware lines ~1200+) — has never been validated on real hardware. Camera-aided tile alignment is the most complex single feature and is unverified.

## 6. Specific questions for Codex

1. **F-1 buck noise:** Is MP1584 switching noise a problem for the analog 5V rail? Suggest LC filter spec or alternate part.
2. **F-2 pull-up placement:** Should R16 sit between ESP32 GPIO and R10, or after R10 on the gate side?
3. **F-3 ESP32-S3 N16R8 pinout:** Confirm GPIO40, 41 are unrestricted for the N16R8 variant (octal PSRAM).
4. **F-5 galvo voltage:** What's the typical input range for cheap "20K PPS galvo scanner kit + driver" boards? Single-ended or differential?
5. **F-9 OV5640 I2C address:** Does it conflict with MPU6050 (0x68) on a shared I2C bus, or is it always 0x3C?
6. **PCB routing:** Given the rats-nest-only state, what's the right next step — auto-route in KiCad, hand-route, or use Freerouter?
7. **Schematic regeneration:** Best practice for re-creating a `.kicad_sch` from an existing `.kicad_pcb` + a documented netlist?
8. **Anything I missed?** Especially: is unity-gain follower really sufficient for the DAC→galvo path? Or is the original gain-stage premise correct and I oversimplified?
